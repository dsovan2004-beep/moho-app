MoHoLocal security and business request release — November 5, 2026

Scope: P0 business/staging permissions, Worker authorization, saved submissions,
ownership claims, moderation evidence, dependency/runtime support and regression checks.
The wider data cleanup and visual redesign remain in docs/ROADMAP.md.

STACK AND RELEASE
Next.js 15.5.29, React 18.3.1, Supabase JS 2.119.0, Tailwind 3, TypeScript 5.
Cloudflare remains the host; Supabase remains the database/Auth/Storage provider.
The deprecated next-on-pages adapter capped Next.js at <=15.5.2. This release uses
OpenNext 1.20.16 and Wrangler 4.157.0 to run the patched app on Cloudflare Workers.
The www.moholocal.com/* Worker route serves the existing hostname; DNS was not changed.
Legacy Cloudflare Pages still exists but is not the active application behind that route.
Node 22+ is required for local builds. Dynamic rendering preserves current database reads.
No R2, new database, payment service, paid plan upgrade or API subscription was added.

Authorization:
- Existing confirmed admin accounts are bootstrapped into a private membership table.
- Browser users cannot self-promote, update another listing/image, or edit city status.
- Staging/raw submissions and the pending-review view are not public APIs.
- Business email/contact_email are denied in direct browser SELECT. Public queries use
  an explicit safe projection; authorized admins use a checked full-projection RPC.
- New tables retain RLS. Requesters can read only their own requests/owner relation;
  direct request inserts/updates are denied. Privileged functions live in a non-exposed
  schema, pin their search paths, and validate identity/authorization internally.
- Review inserts still update rating aggregates through a narrowly scoped trigger.

Submission/claim flow:
- A confirmed account is required before form entry. Browsing/contact stays public.
- Server validates identity using Auth getUser, not editable user metadata.
- Only permitted fields are accepted; bodies and field lengths are bounded.
- Same-origin browser writes use bearer tokens. Database limits are persistent:
  five business requests per account per day, with idempotency keys and claim deduplication.
- The saved pending receipt is confirmed before success is shown. My business requests
  shows the requester's decisions. No ownership flag changes during claim submission.
- Admin approval requires recorded notes and a public evidence URL. Claim approval
  locks the business and assigns one owner atomically. Competing approvals cannot
  replace an existing owner. A nomination/submission does not establish ownership.
- Submission publication creates an approved/checked listing only after explicit human
  review with dated evidence; legacy moderation now records evidence as well.
- The old public arbitrary-recipient notification endpoints return 410. No emails were
  sent during verification. Notification automation can be added using saved records.
- OAuth uses PKCE with the existing callback URL. A safe local return path restores
  the originating form without requiring new redirect allowlist entries.

Worker:
- Manual run and validation routes require POST and a verified admin.
- Missing/invalid tokens and Auth/RPC outages reject the action; no fail-open path.
- Community signals remain available to confirmed residents using a separately
  rate-limited RPC (10/day), always pending; direct raw staging writes remain denied.
- Screenshot intake uses a short-lived admin session token, never anonymous uploads.
  For the local processor provide MOHO_ADMIN_ACCESS_TOKEN in the process environment;
  never commit it. Existing scheduled jobs retain service-role access and four crons.
- Signal-folder anonymous uploads were removed; a restrictive policy prevents older
  permissive authenticated upload policies bypassing the admin-only signals folder.

DEPLOY AND ROLLBACK
Web: npm run deploy (builds OpenNext before Wrangler upload).
Ingestion: npx wrangler deploy --config workers/wrangler.toml from the root.
Preserve existing ingestion secrets; never put its service-role key into client vars.
The two database migrations are already applied; do not reapply them manually.
Keep deployment version IDs in deployment-evidence.json.
Rollback after private-column restriction must use a compatible OpenNext version
with explicit public projections. Do not restore broad database grants or revert to
the old Pages app/old select('*') queries. Prefer a tested forward repair. Before the
final restriction, the two-stage rollout intentionally kept public SELECT compatible.
Subsequent database changes need additive migrations and renewed role-based checks.
